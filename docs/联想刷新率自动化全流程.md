# EcoRefresh —— 全流程记录

## 项目概述

**个人工具**——纯 PowerShell 脚本 + Windows 计划任务，无安装包，无 GUI，无通用性保证。仅在自己 ThinkBook 16+ 上测试通过。

目标：ThinkBook 离电自动切 60Hz 省电，插电切 165Hz。由于 LLT 不支持 ThinkBook，纯 PowerShell + Win32 API + 计划任务实现。

最终成果：`scripts/` 下 3 个脚本 + 1 个 VBS 包装器，`docs/` 下本文档。

### 当前系统实测状态（2026-05-20）

| 属性 | 值 |
|---|---|
| 任务路径 | `\事件查看器任务\离电来电自动刷新率切换` |
| 操作 | `wscript.exe "G:\Autorefresh\scripts\AutoRefreshRate-Trigger.vbs"` |
| 触发器 | Kernel-Power 105, SessionUnlock, Kernel-Power 107, Kernel-Power 507, At startup, At logon |
| 入口 | VBS（GUI 子系统）→ pwsh → Set-RefreshRate.ps1（自动模式） |

### 调用链

```
计划任务 → wscript.exe → AutoRefreshRate-Trigger.vbs → pwsh Set-RefreshRate.ps1
  (事件触发)     ↑ GUI 子系统              ↑ SW_HIDE(0)      单文件, 手动/自动双模式
                不创建控制台窗口              从 CreateProcess
                                            阶段即隐藏
```

## 需求探索阶段

### Fn+Q 性能模式 → 走不通

用户先问了 Fn+Q（性能模式）能否用其他方式触发。调研结论：

- **LenovoLegionToolkit (LLT)**：只支持 Legion / Ideapad Gaming / LOQ，不支持 ThinkBook。原作者 2025-07 归档，社区 fork 继续维护，但兼容范围不变。
- **LegionLaptopToolkitCLI**：同样只支持 Legion 系列。
- **WMI 直调**：Lenovo Gamezone WMI GUID `D320289E-...` 需要对应驱动（Lenovo Energy Management + Vantage Gaming Feature Driver），ThinkBook 不一定带。
- **ThinkBook 的 Intelligent Cooling**：走 Intel DPTF + Windows Power Slider，和 Legion 不走同一套硬件接口，没有现成的第三方 CLI 工具。

→ **放弃 Fn+Q 自动化。转而聚焦 Fn+R（刷新率），因为刷新率是标准 Windows 功能。**

### Fn+R 刷新率 → 可行

刷新率由 Windows 显示子系统管理，任何机型都能用 `user32.dll` 的 `ChangeDisplaySettings` / `EnumDisplaySettings` 控制，无需联想专用驱动。

## P/Invoke 踩坑：DEVMODE 结构体对齐

### 失败 1：托管 struct 直接映射

最直观的做法——用 `Add-Type` 定义 `DEVMODE` struct + `LayoutKind.Sequential` + P/Invoke：

```csharp
[DllImport("user32.dll", CharSet = CharSet.Auto)]
public static extern int EnumDisplaySettings(string lpszDeviceName, int iModeNum, ref DEVMODE lpDevMode);
```

**结果**：`EnumDisplaySettings` 永远返回 0，`GetLastError` 也是 0——无错误码，无数据。

**诊断过程**：
1. 对比系统返回的 `dmSize=188` 和我们 struct 的 `Marshal.SizeOf()=220`，差 32 字节。
2. 强行设 `dmSize=188`、`dmSize=0`，均无效。
3. 换 ANSI 版 `EnumDisplaySettingsA`、Unicode 版 `EnumDisplaySettingsW`、显式设备名 `\\.\DISPLAY1`——全部返回 0。
4. 尝试 `GetDisplayConfigBufferSizes` / `QueryDisplayConfig` CCD API——能获取 3200x2000@60Hz，但改刷新率不如旧 API 直接。

**根因分析**：.NET 的 string marshaling 与 `DEVMODE` 内联字符数组（`TCHAR dmDeviceName[32]`）交互时，在 x64 + CharSet.Auto 下 Marshal 行为不确定。`IntPtr` 作参数时反而正常——说明问题在 Marshal 层，不在 API 层。

→ **最终方案：放弃托管 struct，改用 raw `IntPtr` + 手动偏移读写。**

### 成功方案：Raw IntPtr Buffer

```csharp
[DllImport("user32.dll", SetLastError = true)]
public static extern int EnumDisplaySettingsW(IntPtr lpszDeviceName, int iModeNum, IntPtr lpDevMode);
```

手动分配 512 字节 buffer，按 DEVMODEW 结构体偏移量读写：

| 偏移 | 字段 | 大小 |
|---|---|---|
| 0 | dmDeviceName | 64 (WCHAR[32]) |
| 68 | dmSize | 2 (WORD) |
| 72 | dmFields | 4 (DWORD) |
| 172 | dmPelsWidth | 4 (DWORD) |
| 176 | dmPelsHeight | 4 (DWORD) |
| 184 | dmDisplayFrequency | 4 (DWORD) |

写 `dmSize=188` 后调用 `EnumDisplaySettingsW(IntPtr.Zero, -1, buf)`，成功读到 3200x2000@60Hz。枚举模式 0~N，得到 48/60/75/100/120/165 Hz。

**教训**：Win32 DEVMODE 的 C# 互操作是知名坑。市面上大量 PowerShell 模块（DisplayConfig、ps-display-settings）各家用各家的 struct 定义，撞上不同驱动版本就可能翻车。raw buffer 最稳，代价是代码丑陋。

## 自动化方案演进

### 第一版：轮询任务

`Install-AutoRefreshRate.ps1` 用 `Register-ScheduledTask` 创建任务，三个标准触发器：
- `-AtStartup`（开机）
- `-AtLogOn`（登录）
- `-Once + -RepetitionInterval 3min`（每 3 分钟轮询）

**问题**：用户指出最初讨论的是事件驱动，不是轮询。

### 为什么没直接用事件触发器

`New-ScheduledTaskTrigger` 是 PowerShell ScheduledTask 模块的高级封装，只支持标准触发器（AtStartup、AtLogOn、Daily 等），不支持自定义事件过滤器。要绑 Kernel-Power Event 105，必须操作任务 XML。

### 失败 2：XML 拼接

尝试 `Register-ScheduledTask -Xml` 手工拼接事件触发器 XML，遇到：
```
任务 XML 包含格式不正确或超出范围的值。(14,42):Duration:P99999999DT23H59M59S
```
`[TimeSpan]::MaxValue` 超出了 Task Scheduler 允许的重复持续时间范围。改为 `New-TimeSpan -Days 3650` 解决。

### 失败 3：schtasks + Register-ScheduledTask 混用

在 `Install-AutoRefreshRate.ps1` 里先用 `schtasks /Create /SC ONEVENT` 建事件触发任务，又用 `Register-ScheduledTask` 覆盖同一任务名——结果事件触发器被冲掉。

**根因**：过度设计，想用一个任务承载事件+开机+轮询三个触发器。实际上 `schtasks` 只支持单触发器，`Register-ScheduledTask` 不支持事件触发器——两套 API 各有局限。

### 最终方案：Register-ScheduledTask -Xml

`Register-ScheduledTask` 的 `-Xml` 参数接受完整 Task Scheduler XML，可承载任意触发器组合。安装脚本直接构建包含 5 个触发器的 XML：

- Kernel-Power 105（接通电源）
- Kernel-Power 107（断开电源）
- SessionUnlock（解锁会话）
- BootTrigger（开机）
- LogonTrigger（登录，延迟 10 秒）

再也不用 `schtasks` CLI 和 PowerShell 模块混用，也不用分拆成两个任务。所有触发器在一个任务里，脚本自带去重。

### 当前落地状态

截至 2026-05-20，系统运行 `\事件查看器任务\离电来电自动刷新率切换` 事件任务，由安装脚本通过 XML 注册。

### 第一代修复（失败）

任务触发后闪一个 PowerShell 窗口。

**根因 1**：任务操作中 `-WindowStyle Hidden` 位置错误，被当成传给脚本的参数。

```
# 错误
Arguments: C:\...\Trigger.ps1 -NoProfile -WindowStyle Hidden -File "..."

# 正确
Arguments: -NoProfile -WindowStyle Hidden -File "C:\...\Trigger.ps1"
```

**根因 2**：`Trigger.ps1` 内部用 `& pwsh ... -File $switch` 又起了一个 pwsh 子进程，这个子进程没设 `-WindowStyle Hidden`。

**修复**：改为 `Start-Process -WindowStyle Hidden -Wait`。

**为何仍然闪**：`pwsh.exe` 是控制台子系统（Console Subsystem），`conhost.exe` 会优先为其分配并绘制宿主黑框窗口。pwsh 启动完毕后读到 `-WindowStyle Hidden` 才隐藏——中间的时间差 = 闪烁。**"先上台再拉幕布"。**

### 第二代修复（成功）：VBS 包装器

**原理**：

| 方案 | 入口进程 | 子系统 | 窗口行为 |
|---|---|---|---|
| 旧：`pwsh -WindowStyle Hidden` | pwsh.exe | Console | conhost 先画窗口 → pwsh 初始化 → 隐藏（闪） |
| 新：`wscript.exe Trigger.vbs` | wscript.exe | GUI | Windows 不分配控制台窗口（天生不可见） |

VBS 内部用 `WSH.Run(cmd, 0, True)` 启动 pwsh：
- `0` = `SW_HIDE`，直接写入 `CreateProcess` 的 `STARTUPINFO.wShowWindow`
- 内核从进程"胚胎阶段"就不绘制窗口 → **"穿着隐身衣上台"**

```vbscript
Set ws = CreateObject("WScript.Shell")
ws.Run "pwsh -NoProfile ... Set-RefreshRate.ps1", 0, True
```

### 第三代优化：合并双脚本

旧架构有两个 PS1：
- `AutoRefreshRate-Trigger.ps1`（11 行：检测电源 → 调另一个脚本）
- `Set-RefreshRate.ps1`（66 行：Win32 API 切换）

合并为一个 `Set-RefreshRate.ps1`，双模式：
- `-Hz 60` → 手动切换
- 无参数 → 自动模式：检测电源 → 决定 Hz → 切换

**收益**：消除 `$switch` 路径依赖、减少一次子进程启动、VBS 只需调一个脚本。

## 经验总结

1. **Win32 P/Invoke 在 PowerShell 里优先用 raw IntPtr**：DEVMODE 是知名坑，托管 struct 跨驱动版本不可靠。手动偏移虽然代码丑，但可预期。
2. **schtasks.exe 和 ScheduledTask 模块各管各的**：不要混用更不要覆盖同一个任务名。事件触发器用 schtasks，轮询触发器用 Register-ScheduledTask，分两个任务。
3. **闪窗根因是子系统类型，不是 WindowStyle 参数**：控制台子系统程序（pwsh.exe）无论如何调整参数都有窗口创建延迟。要零闪烁必须用 GUI 子系统入口（wscript.exe）+ `WSH.Run(cmd, 0)`。
4. **先枚举再切换**：`CDS_TEST` 标志位可以在不实际改变显示设置的情况下验证目标刷新率是否可用——所有切换脚本都应该先 TEST 再 APPLY。
5. **去重逻辑前置**：每次触发都读当前刷新率，已是目标 Hz 直接退出，避免无意义切换和屏幕闪烁。
6. **合并薄壳脚本**：两个脚本有调用关系且薄壳脚本只有 11 行时，合并为单文件消除路径耦合。
